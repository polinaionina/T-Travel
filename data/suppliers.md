# Контракты поставщиков и оркестратора

## Схема DTO
```
supplier/
├── models/ — общие типы данных
│   ├── SupplierOperationStatus.java - Результат операции: SUCCESS, FAILED, UNKNOWN.
│   ├── SupplierBookingStatus.java - Состояние брони: NOT_FOUND, RESERVED, CONFIRMED, CANCELLED, UNKNOWN.
│   └── SupplierError.java - Информация об ошибке: код и описание.
├── request/ - запросы от оркестратора поставщику
│   ├── ReserveRequest.java - Запрос на резервирование выбранного предложения
│   ├── ConfirmRequest.java - Запрос на окончательное подтверждение бронирования
│   ├── CancelRequest.java - Запрос на отмену бронирования
│   └── BookingStatusRequest.java - Запрос на получение текущего статуса бронирования
└── response/ — ответы поставщика оркестратору
    ├── ReserveResponse.java - Результат резервирования
    ├── ConfirmResponse.java - Результат подтверждения бронирования
    ├── CancelResponse.java - Результат отмены бронирования
    └── BookingStatusResponse.java - Текущее состояние бронирования у поставщика
```

## Общий принцип взаимодействия

Оркестратор взаимодействует с имитаторами поставщиков посредством HTTP-запросов.

Для каждой операции оркестратор формирует соответствующий Request DTO, отправляет его поставщику и получает Response DTO.

Контракты определяют формат обмена данными. Внутренние сущности оркестратора (`TripOrder`, `OrderComponent`, `ComponentAttempt`) не передаются поставщикам напрямую.

React взаимодействует только с API оркестратора. Прямого взаимодействия веб-интерфейса с имитаторами поставщиков нет.

## Схема операций

| Операция | Метод клиента | Запрос | Ответ | Назначение |
|---|---|---|---|---|
| Резервирование | `reserve()` | `ReserveRequest` | `ReserveResponse` | Зарезервировать выбранное предложение |
| Подтверждение | `confirm()` | `ConfirmRequest` | `ConfirmResponse` | Окончательно подтвердить бронь |
| Отмена | `cancel()` | `CancelRequest` | `CancelResponse` | Отменить ранее созданную бронь |
| Проверка статуса | `status()` | `BookingStatusRequest` | `BookingStatusResponse` | Получить текущее состояние брони |


## Общие модели (`models/`)

### 1. `SupplierOperationStatus.java`

Описывает результат выполнения конкретной операции поставщиком.

Возможные значения:

- `SUCCESS` — операция успешно выполнена.
- `FAILED` — операция завершилась неудачно.
- `UNKNOWN` — результат операции неизвестен, например, из-за таймаута или потери соединения.

**Где используется:** в ответах на операции `reserve`, `confirm` и `cancel`.

**Для чего нужен:** позволяет оркестратору понять, завершилась ли операция успешно, завершилась ошибкой или требует дополнительной проверки.

### 2. `SupplierBookingStatus.java`

Описывает состояние бронирования на стороне поставщика.

Возможные значения:

- `NOT_FOUND` — бронь не найдена.
- `RESERVED` — предложение зарезервировано.
- `CONFIRMED` — бронь подтверждена.
- `CANCELLED` — бронь отменена.
- `UNKNOWN` — поставщик не может определить состояние брони.

**Где используется:** в `BookingStatusResponse`, а также может возвращаться в ответах на операции резервирования, подтверждения и отмены.

**Для чего нужен:** позволяет оркестратору сопоставить состояние брони у поставщика со своим внутренним состоянием компонента.

### 3. `SupplierError.java`

Содержит структурированную информацию об ошибке поставщика:

- код ошибки;
- описание ошибки.

**Где используется:** в Response DTO, если операция завершилась неудачно или поставщик сообщает дополнительную информацию об ошибке.

**Для чего нужен:** позволяет оркестратору классифицировать ошибки, сохранять техническую причину и формировать понятное сообщение для пользователя.

## Запросы (`request/`)

### 1. `ReserveRequest.java`

**Используется в:** `SupplierClient.reserve()`.

**Назначение:** запросить у поставщика резервирование выбранного предложения.

**Содержит:** идентификатор предложения (`offerId`) и другие данные, которые поставщик требует для резервирования.

**Результат:** поставщик возвращает `ReserveResponse`.

### 2. `ConfirmRequest.java`

**Используется в:** `SupplierClient.confirm()`.

**Назначение:** запросить окончательное подтверждение ранее зарезервированного предложения.

**Содержит:** идентификатор бронирования у поставщика (`externalBookingId`) и, если требуется, дополнительные данные для подтверждения.

**Результат:** поставщик возвращает `ConfirmResponse`.

### 3. `CancelRequest.java`

**Используется в:** `SupplierClient.cancel()`.

**Назначение:** запросить отмену ранее созданной брони.

**Содержит:** идентификатор бронирования у поставщика (`externalBookingId`) и, если требуется, дополнительные данные для отмены.

**Результат:** поставщик возвращает `CancelResponse`.

### 4. `BookingStatusRequest.java`

**Используется в:** `SupplierClient.status()`.

**Назначение:** запросить актуальное состояние бронирования у поставщика.

**Содержит:** идентификатор бронирования у поставщика (`externalBookingId`).

**Результат:** поставщик возвращает `BookingStatusResponse`.

## Ответы (`response/`)

### 1. `ReserveResponse.java`

**Возвращается из:** `SupplierClient.reserve()`.

**Назначение:** передать оркестратору результат резервирования.

Предполагаемое содержимое:

- результат операции (`SupplierOperationStatus`);
- состояние бронирования (`SupplierBookingStatus`);
- идентификатор брони у поставщика (`externalBookingId`);
- информация об ошибке (`SupplierError`), если она есть.

При успешном резервировании ожидается:

- `operationStatus = SUCCESS`;
- `bookingStatus = RESERVED`;
- заполненный `externalBookingId`.

Оркестратор сохраняет идентификатор внешней брони и обновляет состояние компонента.

### 2. `ConfirmResponse.java`

**Возвращается из:** `SupplierClient.confirm()`.

**Назначение:** передать оркестратору результат подтверждения бронирования.

Предполагаемое содержимое:

- результат операции (`SupplierOperationStatus`);
- состояние бронирования (`SupplierBookingStatus`);
- информация об ошибке (`SupplierError`), если она есть.

При успешном подтверждении ожидается:

- `operationStatus = SUCCESS`;
- `bookingStatus = CONFIRMED`.

Оркестратор обновляет состояние компонента и продолжает процесс подтверждения заказа.

### 3. `CancelResponse.java`

**Возвращается из:** `SupplierClient.cancel()`.

**Назначение:** передать оркестратору результат отмены бронирования.

Предполагаемое содержимое:

- результат операции (`SupplierOperationStatus`);
- состояние бронирования (`SupplierBookingStatus`);
- информация об ошибке (`SupplierError`), если она есть.

При успешной отмене ожидается:

- `operationStatus = SUCCESS`;
- `bookingStatus = CANCELLED`.

Оркестратор фиксирует результат компенсации компонента.

### 4. `BookingStatusResponse.java`

**Возвращается из:** `SupplierClient.status()`.

**Назначение:** передать оркестратору текущее состояние бронирования у поставщика.

Предполагаемое содержимое:

- состояние бронирования (`SupplierBookingStatus`);
- идентификатор брони у поставщика (`externalBookingId`), если он известен;
- информация об ошибке (`SupplierError`), если поставщик не смог определить состояние.

**Для чего нужен:** используется для разрешения неопределённых результатов операций и восстановления после сбоев.

## Последовательности взаимодействия

### 1. Резервирование предложения

1. Пользователь выбирает предложение в веб-интерфейсе.
2. React отправляет запрос в API оркестратора с идентификатором выбранного предложения.
3. Оркестратор определяет поставщика и формирует `ReserveRequest`.
4. `SupplierClient.reserve()` отправляет запрос поставщику.
5. Поставщик выполняет резервирование и возвращает `ReserveResponse`.
6. Оркестратор преобразует ответ в свой внутренний результат операции.
7. `ComponentProcessor` обновляет состояние компонента, сохраняет результат попытки и записывает событие.

При успешном резервировании компонент получает внутренний статус `RESERVED`.

### 2. Подтверждение бронирования

1. Пользователь отправляет заказ на подтверждение.
2. `BookingService` запускает последовательное подтверждение компонентов.
3. Для очередного компонента `ComponentProcessor` начинает операцию `CONFIRM`.
4. Оркестратор формирует `ConfirmRequest`.
5. `SupplierClient.confirm()` отправляет запрос поставщику.
6. Поставщик возвращает `ConfirmResponse`.
7. Оркестратор преобразует ответ и обновляет состояние компонента.

При успешном подтверждении компонент получает внутренний статус `CONFIRMED`.

### 3. Отмена бронирования

1. Пользователь отменяет заказ либо оркестратор запускает компенсацию после ошибки.
2. `CompensationService` определяет компоненты, бронирования которых необходимо отменить.
3. `ComponentProcessor` начинает операцию `CANCEL`.
4. Оркестратор формирует `CancelRequest`.
5. `SupplierClient.cancel()` отправляет запрос поставщику.
6. Поставщик возвращает `CancelResponse`.
7. Оркестратор преобразует ответ и обновляет состояние компонента.

При успешной отмене компонент получает внутренний статус `CANCELLED`.

### 4. Проверка статуса бронирования

1. Оркестратор получает неопределённый результат операции, например, из-за таймаута.
2. `UnknownResolver` или механизм восстановления инициирует проверку состояния брони.
3. Оркестратор формирует `BookingStatusRequest`.
4. `SupplierClient.status()` отправляет запрос поставщику.
5. Поставщик возвращает `BookingStatusResponse`.
6. `UnknownResolver` анализирует состояние бронирования и переводит компонент в соответствующий внутренний статус.

Проверка статуса позволяет избежать повторного выполнения операции, если предыдущий запрос фактически выполнился, но ответ не дошёл до оркестратора.

## Место интеграционного слоя в оркестраторе

Текущее расположение классов:

```text
ru.ttravel.orchestrator/
├── providers/
│   ├── SupplierClient.java
│   ├── HttpSupplierClient.java
│   ├── StubSupplierClient.java
│   ├── SupplierReservation.java
│   └── exceptions/
├── booking/
│   ├── BookingService.java
│   ├── CompensationService.java
│   ├── ComponentProcessor.java
│   └── UnknownResolver.java
└── ...
```

Ответственность классов:

| Класс | Ответственность |
|---|---|
| `SupplierClient` | Общий интерфейс операций с поставщиком |
| `HttpSupplierClient` | Отправка HTTP-запросов и получение ответов |
| `StubSupplierClient` | Тестовая реализация без обращения к имитаторам |
| `SupplierReservation` | Внутренняя модель результата бронирования, если она потребуется |
| `ComponentProcessor` | Управление состояниями компонентов, попытками и событиями |
| `BookingService` | Координация последовательного подтверждения компонентов |
| `CompensationService` | Координация отмены бронирований |
| `UnknownResolver` | Разрешение неопределённого результата через проверку статуса |

Интеграционный слой не должен самостоятельно менять состояния JPA-сущностей заказа и компонентов. Он отвечает за взаимодействие с поставщиком и передачу результата вызывающему сервису. Изменение внутренних состояний выполняет бизнес-слой оркестратора.

## Важные правила взаимодействия

- Оркестратор является единственной точкой взаимодействия между веб-интерфейсом и поставщиками.
- Поставщики не взаимодействуют напрямую с React.
- DTO контрактов не должны зависеть от JPA-сущностей оркестратора.
- Идентификатор бронирования у поставщика (`externalBookingId`) сохраняется оркестратором и используется для последующих операций.
- `SupplierOperationStatus.UNKNOWN` означает, что результат конкретного запроса неизвестен. Это не означает, что операция точно не выполнилась.
- `SupplierBookingStatus.UNKNOWN` означает, что поставщик не может определить текущее состояние бронирования.
- При неопределённом результате оркестратор должен сначала запросить статус брони, а не безусловно повторять операцию.
- Ошибки поставщика преобразуются во внутренние результаты оркестратора.
- Повторные запросы должны быть идемпотентными либо иметь механизм защиты от дублирования бронирований.

## Контракты получения предложений

Текущий набор DTO описывает операции над уже выбранным предложением и созданной бронью. Для получения списка предложений необходим отдельный контракт.

Предлагается добавить(пока предварительно, можно не добавлять):

```text
supplier/
├── request/
│   └── OffersRequest.java
└── response/
    └── OfferResponse.java
```

`OffersRequest` используется для запроса списка предложений с параметрами поиска.

`OfferResponse` описывает одно предложение поставщика. Он должен содержать общие поля, необходимые оркестратору (например, идентификатор предложения, тип компонента, цену и валюту), а также данные, специфичные для конкретного типа предложения.

Оркестратор получает предложения от поставщика, преобразует их в API DTO для React и сохраняет снимок выбранного предложения (`offer_snapshot`) при резервировании компонента.

**Важно:** точный состав полей `OffersRequest`, `OfferResponse` и всех остальных DTO должен быть согласован с реализацией имитаторов. Приведённые выше описания назначения не заменяют спецификацию конкретных JSON-полей.
