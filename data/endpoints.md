# Эндпоинты

[Контракты](contracts.md) содержат параметры, примеры JSON и справочник кодов ошибок. Переходы заказа описаны в [сценарии](userflow.md) и на [диаграмме состояний](image.png).

## API оркестратора для фронтенда

Базовый путь — `/`.

### Предложения

| Метод и путь | Назначение | Успешный ответ | Ошибки |
|---|---|---|---|
| `GET /offers` | Найти предложения поставщиков для текущего шага | `200`, [результат поиска](contracts.md#предложения) | `400`, `503` |

### Заказы

| Метод и путь | Действие | Успешный ответ | Ошибки |
|---|---|---|---|
| `POST /orders` | Создать пустой заказ в `DRAFT` | `201` при создании, `200` с текущим состоянием при повторе с теми же `userId` и `Idempotency-Key` | `400` |
| `PUT /orders/{id}/components/{type}` | Выбрать или заменить предложение в `DRAFT` либо выбрать замену для проблемного компонента в `ACTION_REQUIRED` | `200`, выбранный компонент в `RESERVED` | `400`, `404`, `409 OFFER_UNAVAILABLE`, `409 INVALID_STATUS_TRANSITION`, `503` |
| `POST /orders/{id}/submit` | Запустить подтверждение из `DRAFT` или `ACTION_REQUIRED` | `202`, заказ в `CONFIRMING`. Повтор в `CONFIRMING` возвращает текущее состояние с `202` | `404`, `409 ORDER_NOT_READY`, `409 INVALID_STATUS_TRANSITION` |
| `GET /orders/{id}` | Получить текущее состояние заказа | `200` | `404` |
| `GET /orders` | Получить [страницу заказов](contracts.md#список-заказов) пользователя. Параметр `userId` обязателен, `status`, `page` и `size` опциональны | `200` | `400` |
| `POST /orders/{id}/cancel` | Отменить заказ из `DRAFT`, `PAYMENT_FAILED` или `ACTION_REQUIRED` | `202`, из `ACTION_REQUIRED` заказ переходит в `CANCELLING`, из `DRAFT` и `PAYMENT_FAILED` — в `CANCELLED` после снятия броней | `400`, `404`, `409 INVALID_STATUS_TRANSITION` |

Маршруты для отдельного заказа возвращают [`OrderView`](contracts.md#orderview). Команды изменения заказа могут также вернуть `409 CONCURRENT_MODIFICATION`.

- **Выбор.** Оркестратор дожидается результата резервирования. При замене в `DRAFT` предыдущая бронь этого типа в `RESERVED` снимается перед созданием новой. В `ACTION_REQUIRED` выбор замены сохраняет статус заказа до повторного `submit`.
- **Подтверждение.** Для `submit` актуальные компоненты должны быть в `RESERVED` или `CONFIRMED`. В фоне оркестратор подтверждает брони по `stepNo`, пропуская уже подтверждённые. Отказ при подтверждении компонента переводит заказ в `ACTION_REQUIRED`, и фронтенд открывает шаг из `actionRequiredFor`. Повторный `submit` во время подтверждения не запускает процесс заново.
- **Оплата.** Когда все компоненты подтверждены, оркестратор переводит заказ в `PAYMENT_PENDING`. Результат оплаты переводит его в `CONFIRMED` или `PAYMENT_FAILED`.
- **Отмена.** Из `ACTION_REQUIRED` оркестратор снимает брони в фоне в обратном порядке шагов. Если все брони сняты, заказ переходит из `CANCELLING` в `CANCELLED`. Если снять бронь не удалось, заказ переходит в `NEEDS_HELP` и возвращается в `CANCELLING` после снятия брони администратором.
- **Истечение срока.** Оркестратор запускает те же переходы отмены по таймауту заказа. Если истекает срок отдельной брони во время сборки, фронтенд получает шаг для повторного выбора через `actionRequiredFor`.

### Журнал и обновления

| Метод и путь | Назначение | Успешный ответ | Ошибки |
|---|---|---|---|
| `GET /orders/{id}/events` | Журнал для временной шкалы. Можно передать `componentId` для фильтрации | `200`, массив [событий](contracts.md#событие-заказа) по времени | `404` |
| `GET /orders/{id}/stream` | Обновления в реальном времени | `200`, `text/event-stream` | `404` |
| `GET /orders/{id}/components/{componentId}/attempts` | История обращений к поставщику по компоненту, включая повторы | `200`, массив [попыток](contracts.md#попытка-обращения-к-поставщику) | `404` |

События SSE отправляются после записи в журнал. Получив `order-event`, фронтенд обновляет состояние через `GET /orders/{id}`.

### Уведомления

| Метод и путь | Назначение | Успешный ответ | Ошибки |
|---|---|---|---|
| `GET /notifications` | Уведомления пользователя. Параметр `userId` обязателен, `unread=true/false` опционален | `200`, массив [уведомлений](contracts.md#уведомление) | `400` |
| `POST /notifications/{id}/read` | Отметить уведомление прочитанным. Запрос без тела | `204`, без тела | `404` |

## API имитаторов поставщиков

Базовый путь — `/{supplier}`, где `supplier` принимает значения `airline`, `hotel`, `insurance`, `transfer`. Маршруты вызывает оркестратор. Формы сообщений описаны в [документации поставщиков](suppliers.md) и [Java DTO](../contracts/supplier).

| Метод и путь | Назначение | Успешный ответ | Ошибки |
|---|---|---|---|
| `GET /{supplier}/offers` | Найти предложения. Параметры поиска зависят от поставщика | `200`, список предложений | `400` |
| `POST /{supplier}/reserve` | Зарезервировать предложение | `200`, `ReserveResponse` с идентификатором брони при успехе | `400`, `409`, `503` |
| `POST /{supplier}/confirm/{id}` | Подтвердить бронь | `200`, `ConfirmResponse` | `404`, `409`, `503` |
| `POST /{supplier}/cancel/{id}` | Снять бронь, в том числе при компенсации | `200`, `CancelResponse` | `404`, `503` |
| `GET /{supplier}/status/{id}` | Проверить состояние брони по известному внешнему идентификатору | `200`, `BookingStatusResponse` | `404` |

`{id}` в маршрутах поставщика — `externalBookingId`. Оркестратор передаёт идентификатор операции `{orderId}:{componentId}:{operation}` в `requestId` и записывает его в `ComponentAttempt`. Для `reserve` это же значение используется в заголовке `Idempotency-Key`. Повтор `reserve` с тем же ключом возвращает ту же бронь. Повторный `cancel` безопасен.

Если `reserve` завершился таймаутом до получения `externalBookingId`, проверка по пути `/status/{id}` невозможна. Для этого случая нужно согласовать поиск брони по исходному `requestId` операции `RESERVE`.

### Управление сбоями

| Метод и путь | Назначение | Запрос | Успешный ответ |
|---|---|---|---|
| `POST /sim/faults/{supplier}` | Включить режим сбоя | `mode`, `rate`, `delayMs` | `200`, текущая настройка |
| `GET /sim/faults/{supplier}` | Посмотреть текущий режим | Без тела | `200`, текущая настройка |
| `DELETE /sim/faults/{supplier}` | Вернуть нормальную работу | Без тела | `204`, без тела |

| `mode` | Поведение |
|---|---|
| `OK` | Отвечает нормально |
| `FAIL` | Возвращает `503` |
| `LATENCY` | Отвечает с задержкой `delayMs` |
| `PRICE_CHANGE` | Меняет цену при подтверждении |
| `SUCCESS_BUT_TIMEOUT` | Выполняет операцию, ответ до оркестратора не доходит |

Например, `POST /sim/faults/hotel` с телом `{"mode":"FAIL","rate":1.0}` заставляет каждую попытку резервирования гостиницы завершаться ошибкой.

Для режима `PRICE_CHANGE` нужно согласовать, как поставщик передаёт новую цену при подтверждении. В текущем `ConfirmResponse` отдельных полей цены и валюты нет.
